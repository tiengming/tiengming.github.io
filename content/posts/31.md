## 🧩 起因：上架一个方案，比写方案还累

前段时间把自己改的雾凇·墨奇双拼精简版（`moqi_wan_flypymo`）发到曦码的扩展商店，流程大概是这样的：

1. 把方案打包成 zip，传到 GitHub Release；
2. 算 `sha256`、文件大小；
3. 去 `xime-index` 仓库 `src/rimes/` 下写一份 YAML，填版本、日期、changelog、下载地址、哈希；
4. 确认 `id` 和方案里的 `schema_id` 一致、`dependencies` 写的是别人的 `schema_id` 而不是显示名；
5. 本地检查一遍 zip 里有没有 `.schema.yaml`、`.dict.yaml`，有没有混进 `build/`、`userdb/`；
6. 从 `upstream/main` 拉分支、只提交 `src/`、开 PR；
7. 等 CI，发现它根本不跑（只改 `src/` 的 PR 不触发检查），于是又得自己确认一遍；
8. 合并后等机器人重建索引，再去 raw 上核对有没有上线。

这些步骤没有一步难，但**每一步都能写错**。而且它们和「写方案」是两种完全不同的工作：一个要你对词库和编码有判断，一个纯粹是核对、抄写、比对哈希。

我写过一次之后就想：能不能把后半段交给 AI？

## 🤖 Agent Skills 是什么

不是又一个命令行工具，而是给 AI 编程助手用的「技能包」。

一个 Skill 通常就是一个目录：

```text
xime-index-submit/
├── SKILL.md              # 说明书：什么时候用、分几步、哪些必须停下来问人
├── scripts/              # 真正干活的 Python 脚本
│   ├── preflight.py      # 预检
│   ├── asset_meta.py     # 下载附件、算哈希
│   ├── validate_entry.py # 条目校验
│   ├── tools.py          # 跨平台找 gh、读登录状态
│   └── lib.py            # 共用逻辑
├── templates/            # 五类条目的 YAML 模板
└── references/           # 分类型规则、排错手册、上游规则快照
```

放到 `~/.agents/skills/` 之后，你说「用 xime-index-submit 把这个仓库的方案上架」，助手就会读 `SKILL.md`，按里面的流程调脚本。

关键区别在于：**它不是「一键上架」的按钮**。按钮只能处理你预设好的情况，而真实上架充满了判断——这个仓库是方案还是布局？主方案是哪一个？依赖要不要声明？Release 里没有附件怎么办？CI 为什么不触发？

我的拆法是：

> **能算的交给脚本，要判断的留给模型，不可逆的留给人。**

- 脚本负责确定性的部分：下载、`sha256`、zip 路径安全、YAML 字段校验；
- 模型负责看仓库、选类型、读 README、决定依赖、排查失败；
- 人只负责点头：`git push` 和开 PR 之前必须确认。

## 🗺️ 它按九步走

| 阶段 | 做什么 |
| --- | --- |
| 0 预检 | 检查 `xime-index` 克隆、必需工具、上游规则有没有变化 |
| 1 分类 | 布局 / 插件 v2 / 旧版插件 / 输入方案 / 模型，新建还是更新 |
| 2 产物校验 | zip 结构、路径安全、`manifest.json`、`schema_id` |
| 3 发布与取数 | **下载真实的 Release 附件**，实测 `sha256`、`size`、`sizeBytes` |
| 4 生成条目 | 按模板写 `src/<类型>/<id>.yaml` |
| 5 本地验证 | 条目校验 + `ci-update.py --check/--verify`，确认 diff 只含 `src/` |
| 6 提交 PR | 建分支、提交，**push 和开 PR 都要人确认** |
| 7 盯 CI | 读检查结果，失败就定位原因继续修 |
| 8 合并后 | 等维护者合并，确认索引重建完成 |

其中第 3 步是我最在意的：**哈希必须来自「实际下载下来的那个附件」，不是本地构建产物**。

因为用户安装时下的是 Release 附件，不是你的工作目录。本地算一百遍，附件传错了照样全错。

## 🚀 用起来是什么样

安装：

```bash
npx skills add tiengming/xime-skills --skill xime-index-submit -g
```

`-g` 装到用户级目录 `~/.agents/skills/`，所有项目可用。

然后直接把链接丢给助手：

```text
使用 xime-index-submit 技能，把这个仓库的输入方案上架到曦码扩展商店：
https://github.com/you/rime-scheme
```

其他常见说法：

- `用 xime-index-submit 上架这个布局的最新 Release：https://github.com/you/my-layout`
- `用 xime-index-submit 把 my_schema 更新到 1.3.0，新 tag 和附件都已发布`
- `用 xime-index-submit 修一下这个 PR 的 CI 失败：<链接>`

## 🧪 一次真实上架

第一次实战就是开头的墨奇双拼 Lite，过程里有三个坑，正好说明「判断」这件事为什么不能写死：

**一、Release 是空的。**
仓库有 tag、有 Release 说明，但附件列表是空的。技能停下来告诉我：没有可下载的资产，请先上传。我传完，它重新下载、比对哈希，一致才继续。如果它自作聪明拿 tag 归档顶上，后面内容一变，哈希就废了。

**二、依赖不是「看到什么就写什么」。**
方案里写了 `dependencies: [reverse_moqima, radical_flypy, emoji]`，但三个反查方案都打包在同一个 zip 里。索引里如果照着声明依赖，用户安装时就会去找根本不存在的商店条目。所以条目写成 `dependencies: []`——这个判断来自「包里有没有」，而不是「文件里写了什么」。

**三、包会覆盖用户主题。**
这个仓库除了方案，还带了 `xime.custom.yaml`、`themes/`、`fonts/`。装方案会顺带把用户的键盘主题换成作者那套。技能没有替我删文件，而是把它写进条目的 `warning` 字段，让用户在商店里就能看到。

顺便说，这次实战还**反过来修了工具本身**：`validate_entry.py` 原来只读 YAML 顶层的 `schema_id`，而标准 Rime 方案写在 `schema:` 段里，导致任何真实方案文件都会误报「缺少 schema_id」。发现后改成了两种写法都识别，补了三个测试，v0.2.0 一起发出去。

## 🧱 边界：哪些事它绝不做

这部分写得比功能还细，因为让 AI 碰 Git 仓库，最怕的就是「顺手」。

| 动作 | 规则 |
| --- | --- |
| 改文件、跑校验、本地 commit | 可以直接做 |
| `git push` | 展示 diff 和命令，**等明确同意** |
| 创建 PR | 展示标题和正文，**再确认一次** |
| 强推、删分支 / tag / Release | 默认拒绝，单独确认 |
| 合并 PR | 不做，维护者决定 |
| 读取或写入 token | 不做，也不落盘 |
| 执行下载的插件 / 布局 | 不做，只读结构、只算哈希 |

还有一条是断网时的规矩：脚本下载失败会判断是「资产不存在」还是「网络不通」。网络问题时提示是否需要代理，**只列已设置的代理变量名，不打印值**，也绝不猜代理地址——更不允许因为连不上就改用本地哈希、跳过校验。

## 🧠 写技能和写代码，差别在哪

写完第一版我最大的感受是：**技能的文档就是代码**。

`SKILL.md` 里每一句「停止条件」都会被真的执行。写「sha256 不一致时停下来确认」，它就会停；写「缺 License 就默认 MIT」，它下次真的会编一个 MIT 出来。所以文档里不能有含糊的余地，得把「什么情况下不许继续」写死。

另外，技能也需要测试。这个仓库现在有 131 个用例，跑在 Python 3.10 / 3.12 上：

```bash
python3 -m unittest discover -s tests -v
```

覆盖的东西其实很无聊：zip 路径穿越、符号链接、`schema_id` 不一致、`sha256` 不符、代理提示、跨平台找 `gh`……但正是这些无聊的检查，让「交给 AI」这件事变得可以信任。

## 🔁 后来的两个版本

- **v0.2.0**：修 `schema_id` 解析；网络受阻时主动提示代理。
- **v0.3.0**：跨平台探测 `gh`——Windows 的 `%LOCALAPPDATA%\Programs\GitHub CLI`、Scoop / Chocolatey / WinGet，macOS 的 `/opt/homebrew/bin`，Linux 的 `~/.local/bin`、`/snap/bin`；找到后还会检查登录状态和 scope，区分「没装 / 没登录 / 缺 `repo` 权限」。顺便把「装了但不在 PATH」单独标出来——这坑我自己就踩了。
